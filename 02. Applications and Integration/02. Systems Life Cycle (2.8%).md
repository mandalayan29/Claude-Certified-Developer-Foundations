## 📘 Introduction

When you build an application that uses Claude (or any AI model), you don't just write code and stop. You follow a **cycle** of steps from idea to daily use and beyond. This cycle is called the **Systems Life Cycle** (also called SDLC — Systems/Software Development Life Cycle).

This tutorial explains:
- What Systems Life Cycle means
- Common frameworks used in the industry
- How each phase applies when building Claude-powered apps
- Code examples for each phase

---

## 1. What is Systems Life Cycle?

**Definition:** Systems Life Cycle is a set of stages that a system (software, app, or AI solution) goes through — from the first idea to the day it is retired.

Think of it like building and running a restaurant:
1. You plan the menu (**Planning**)
2. You design the kitchen (**Design**)
3. You cook and prepare (**Development**)
4. You taste-test the food (**Testing**)
5. You open for customers (**Deployment**)
6. You run daily operations (**Operation**)
7. You update the menu and fix issues (**Maintenance**)
8. Eventually, you may close and replace it with a new restaurant (**Retirement**)

The same idea applies to any Claude-based application.

---

## 2. The 7 Phases of Systems Life Cycle

```
┌──────────┐   ┌────────┐   ┌─────────────┐   ┌─────────┐
│ Planning │ → │ Design │ → │ Development │ → │ Testing │
└──────────┘   └────────┘   └─────────────┘   └─────────┘
                                                     │
┌────────────┐   ┌───────────┐   ┌─────────────┐    │

└────────────┘   └───────────┘   └─────────────┘
       ↑                              │

```

Let's go through each phase, one by one, using a real example: **Building a Customer Support Chatbot with Claude.**

---

### Phase 1: Planning

**Goal:** Understand *why* you are building the system and *what* it must do.

Key questions to answer:
- What problem are we solving?
- Who are the users?
- What data will Claude need access to?
- What are the budget and time limits?
- What safety and compliance rules apply? (e.g., no sharing of personal data)

**Example:**
> We are building a chatbot to answer customer questions about order status. It must connect to our order database and respond politely, in under 3 seconds.

**Deliverables from this phase:**
- Requirements document
- Success criteria (e.g., "90% of questions answered correctly")
- Risk assessment (e.g., "Claude should never give refund amounts directly")

---

### Phase 2: Design

**Goal:** Decide *how* the system will be built.

In Claude applications, design includes:
- Choosing the right **Claude model** (e.g., Claude Opus for complex reasoning, Claude Haiku for fast/cheap replies)
- Designing the **system prompt**
- Planning **tool use / function calling** (if Claude needs to call APIs)
- Designing conversation flow and fallback behavior
- Planning for **guardrails** (content filtering, refusal handling)

**Example: Designing the system prompt**

```text
You are a helpful customer support assistant for ShopEasy.
- Only answer questions about order status, shipping, and returns.
- Never share internal database details.
- If you are unsure, say "Let me connect you to a human agent."
```

**Example: Deciding on architecture**

```
User → Frontend App → Backend Server → Claude API → Order Database (via Tool Use)
```

---

### Phase 3: Development

**Goal:** Build the actual system — write code, create prompts, integrate APIs.

This is where you:
- Write the code that calls the Claude API
- Build **prompt templates**
- Set up **tool definitions** (function calling)
- Handle errors and edge cases

**Example: Basic Claude API call (Python)**

```python
import anthropic

client = anthropic.Anthropic(api_key="YOUR_API_KEY")

response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=500,
    system="You are a helpful customer support assistant for ShopEasy.",
    messages=[
        {"role": "user", "content": "Where is my order #12345?"}
    ]
)

print(response.content)
```

**Example: Adding a Tool (Function Calling)**

```python
tools = [
    {
        "name": "get_order_status",
        "description": "Fetch the current status of a customer order",
        "input_schema": {
            "type": "object",
            "properties": {
                "order_id": {"type": "string"}
            },
            "required": ["order_id"]
        }
    }
]

response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=500,
    tools=tools,
    messages=[
        {"role": "user", "content": "Where is my order #12345?"}
    ]
)
```

During development, teams usually use **version control** (like Git) to track changes to code AND to prompts.

```bash
git init
git add prompts/support_prompt_v1.txt
git commit -m "Initial version of support system prompt"
```

### Phase 4: Testing

**Goal:** Make sure the system works correctly, safely, and reliably *before* real users see it.

For Claude applications, testing includes:

| Test Type | What it Checks |
|---|---|
| **Functional Testing** | Does Claude answer correctly? |
| **Prompt Evaluation** | Does the prompt produce consistent, good answers across many inputs? |
| **Red Teaming** | Can users trick Claude into bad behavior (jailbreaks)? |
| **Load Testing** | Does the system work when 1000 users ask at once? |
| **Regression Testing** | Did a prompt change break something that used to work? |

**Example: Simple evaluation script**

```python
test_cases = [
    {"input": "Where is my order #123?", "expected_keyword": "status"},
    {"input": "Can you give me a refund of $500?", "expected_keyword": "human agent"},
]

for case in test_cases:
    response = client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=200,
        system="You are a support assistant. Never approve refunds directly.",
        messages=[{"role": "user", "content": case["input"]}]
    )
    text = response.content[0].text
    passed = case["expected_keyword"] in text.lower()
    print(f"Test: {case['input']} -> {'PASS' if passed else 'FAIL'}")
```

> 💡 **Exam Tip:** This step where you evaluate model outputs against expected behavior is often called **"eval"** in AI development. It's a key part of the testing phase for LLM-based systems.

---

### Phase 5: Deployment

**Goal:** Release the system so real users can use it.

Common deployment strategies:

| Strategy | Description |
|---|---|
| **Big Bang** | Release to everyone at once |
| **Phased Rollout** | Release to a small % of users first |
| **Blue-Green Deployment** | Run old and new versions side by side, switch traffic when ready |
| **Canary Release** | Send a small amount of traffic to the new version to check for issues |

**Example: Simple deployment checklist**

```markdown
- [ ] API keys stored securely (not hardcoded)
- [ ] Rate limiting configured
- [ ] Logging enabled
- [ ] Fallback response ready if Claude API fails
- [ ] Monitoring dashboard set up
```

**Example: Using environment variables for safe deployment**

```python
import os
import anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
```

---

### Phase 6: Operation

**Goal:** Keep the system running smoothly every day.

This includes:
- Monitoring response times and errors
- Tracking API usage/cost
- Watching for unusual behavior (e.g., users trying to jailbreak Claude)
- Collecting user feedback

**Example: Simple logging for monitoring**

```python
import logging

logging.basicConfig(filename="claude_app.log", level=logging.INFO)

def call_claude(user_message):
    try:
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=500,
            messages=[{"role": "user", "content": user_message}]
        )
        logging.info(f"SUCCESS - input: {user_message}")
        return response
    except Exception as e:
        logging.error(f"FAILURE - input: {user_message}, error: {e}")
        return None
```

**Key Metrics to Watch:**
- Latency (response time)
- Token usage / cost
- Error rate
- User satisfaction score

---

### Phase 7: Maintenance

**Goal:** Fix issues, improve prompts, and update the system over time.

Types of maintenance:

| Type | Example |
|---|---|
| **Corrective** | Fixing a bug where Claude gives wrong shipping info |
| **Adaptive** | Updating prompt because company policy changed |
| **Perfective** | Improving prompt to make responses friendlier |
| **Preventive** | Adding better guardrails before a problem happens |

**Example: Updating a prompt (version tracking)**

```text
# prompts/support_prompt_v2.txt
You are a helpful customer support assistant for ShopEasy.
- Only answer questions about order status, shipping, and returns.
- Never share internal database details.
- If asked about refunds over $100, escalate to a human agent.
- Always respond in a warm, friendly tone.
```

```bash
git add prompts/support_prompt_v2.txt
git commit -m "v2: Added refund escalation rule and friendlier tone"
```

> 💡 **Exam Tip:** Just like code, **prompts should be version-controlled**, tested before release, and rolled back if they cause problems.

---

### Phase 8 (Optional): Retirement

**Goal:** Safely shut down or replace the system when it's no longer needed.

Examples:
- Migrating from an old Claude model version to a newer one
- Archiving old conversation logs (following data retention rules)
- Informing users of the change

```markdown
Retirement Checklist:
- [ ] Notify users of the change/shutdown date
- [ ] Export/archive important data
- [ ] Redirect traffic to new system
- [ ] Revoke old API keys
```

## 3. Common Life Cycle Frameworks

Different organizations use different frameworks to manage these phases.

### 3.1 Waterfall Model
- Phases happen **one after another**, in strict order.
- Good for projects with clear, fixed requirements.
- Bad for AI projects because prompts often need many rounds of testing and change.

```
Planning → Design → Development → Testing → Deployment → Maintenance
```

### 3.2 Agile Model
- Work is done in **short cycles (sprints)**, usually 1-2 weeks.
- Teams build a small part, test it, get feedback, and improve.
- **Most common approach for Claude application development**, because prompt engineering needs constant iteration.

```
Sprint 1: Build basic chatbot → Test → Feedback
Sprint 2: Add tool use → Test → Feedback
Sprint 3: Improve prompt safety → Test → Feedback
```

### 3.3 DevOps
- Combines **Development** and **Operations** into one continuous cycle.
- Focus on automation: automatic testing, automatic deployment (CI/CD).

```
Code → Build → Test → Release → Deploy → Monitor → (back to Code)
```

### 3.4 LLMOps / MLOps (Modern Framework for AI Systems)
- A newer version of DevOps, made specifically for AI/LLM applications.
- Adds AI-specific steps:
  - **Prompt versioning**
  - **Model evaluation pipelines**
  - **Guardrail testing**
  - **Cost/token monitoring**
  - **Human feedback loops (RLHF-style feedback for improving prompts)**

```
┌─────────────────┐     ┌──────────────┐     ┌────────────┐
│ Prompt/Model Dev│ →   │  Evaluation  │  →  │ Deployment │
└─────────────────┘     └──────────────┘     └────────────┘
        ↑                                          │
        └──────────── Monitoring & Feedback ───────┘
```

> 💡 **Exam Tip:** LLMOps is basically DevOps + special care for prompts, model versions, and AI safety testing. Expect exam questions comparing DevOps vs LLMOps.

## 4. Applying Life Cycle to CI/CD (Continuous Integration/Continuous Deployment)

Modern Claude applications often use **CI/CD pipelines** to automate testing and deployment.

**Example: Simple CI/CD pipeline (conceptual YAML)**

```yaml
name: Claude App Pipeline

on: [push]

jobs:
  test:
    steps:
      - name: Run prompt evaluation tests
        run: python run_eval_tests.py

  deploy:
    needs: test
    steps:
      - name: Deploy to production
        run: ./deploy.sh
```

This means:
1. Every time code/prompts change → automatically run tests
2. If tests pass → automatically deploy
3. If tests fail → stop and alert the team

## 5. Quick Comparison Table (Good for Exam Memorization)

| Framework | Style | Best For |
|---|---|---|
| Waterfall | Sequential, fixed steps | Simple, well-defined projects |
| Agile | Iterative, short cycles | Fast-changing requirements (like prompt engineering) |
| DevOps | Continuous, automated | Frequent releases, strong automation |
| LLMOps | DevOps + AI-specific steps | AI/Claude-based applications |

---

## 6. Key Takeaways (Exam Summary)

✅ Systems Life Cycle = Planning → Design → Development → Testing → Deployment → Operation → Maintenance → (Retirement)

✅ For Claude apps, **prompts are treated like code** — they need versioning, testing, and review.

✅ **Agile** is the most common approach for AI application teams because prompts need constant refinement.

✅ **LLMOps** extends DevOps with AI-specific practices: prompt evaluation, guardrail testing, and monitoring for model drift/cost.

✅ Testing for Claude apps includes **functional testing + red teaming + evaluation scripts**, not just normal software testing.

✅ Maintenance in AI systems often means **updating prompts or switching model versions**, not just fixing code bugs.

## 7. Practice Questions (Self-Check)

1. **Q:** Which life cycle phase involves writing the system prompt and setting up tool definitions?
   **A:** Design phase

2. **Q:** What is the term for testing an AI model's output against expected results?
   **A:** Evaluation ("eval")

3. **Q:** Which framework combines Development and Operations into a continuous loop with automation?
   **A:** DevOps

4. **Q:** What extra practices does LLMOps add on top of DevOps?
   **A:** Prompt versioning, model evaluation pipelines, guardrail testing, and cost/token monitoring

5. **Q:** In which phase would you write a rollback plan in case a new prompt breaks user experience?
   **A:** Maintenance phase (with proper version control set up during Development)
