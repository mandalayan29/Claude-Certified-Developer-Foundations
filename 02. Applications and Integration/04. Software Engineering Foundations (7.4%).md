## 2. REST APIs — The Standard Way Systems Talk to Each Other

A **REST API** (Representational State Transfer) is a common pattern for letting systems communicate over HTTP using predictable, resource-based URLs and standard HTTP methods.

| HTTP Method | Meaning | Example |
|---|---|---|
| `GET` | Retrieve data | `GET /tickets/123` — fetch ticket 123 |
| `POST` | Create new data | `POST /tickets` — create a new ticket |
| `PUT` / `PATCH` | Update existing data | `PATCH /tickets/123` — update ticket 123 |
| `DELETE` | Remove data | `DELETE /tickets/123` — delete ticket 123 |

**Simple example — a REST endpoint that calls Claude:**

```python
from fastapi import FastAPI
import anthropic

app = FastAPI()
client = anthropic.Anthropic()

@app.post("/summarize-ticket")
def summarize_ticket(ticket_text: str):
    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=300,
        messages=[{"role": "user", "content": f"Summarize this ticket: {ticket_text}"}]
    )
    return {"summary": response.content[0].text}
```

The Claude API itself (from Task 2.3) is a REST API — this is why the same HTTP concepts (status codes, methods, headers) apply when calling it directly.

> **Exam tip:** Status codes matter for error handling — e.g., `429` (rate limited) should trigger a retry with backoff, while `400` (bad request) means your request itself needs fixing, not retrying blindly.

## 3. JSON — The Data Format Behind Almost Everything

**JSON** (JavaScript Object Notation) is the standard format for structuring data sent to and from APIs, including the Claude API.

```json
{
  "model": "claude-sonnet-4-6",
  "max_tokens": 1024,
  "messages": [
    {"role": "user", "content": "Summarize this ticket"}
  ]
}
```

**Why it matters here:** when you ask Claude to return **structured output** (e.g., for downstream code to consume, as seen with PydanticAI in Task 1.3), you're asking it to produce valid JSON that matches a schema.

**Simple example — validating Claude's JSON output:**

```python
import json

raw_text = response.content[0].text
try:
    data = json.loads(raw_text)   # parse Claude's output as JSON
except json.JSONDecodeError:
    # Claude didn't return valid JSON — handle the error, maybe retry
    data = None
```

> ⚠️ **Anti-Pattern: Trusting model output as valid JSON without checking**
> Directly parsing a model's text output as JSON without error handling can crash your application if the model returns malformed output. Always validate/parse defensively, or use structured-output features that enforce a schema.

## 4. Asynchronous Programming — Not Waiting Around

**Asynchronous (async) programming** lets your program continue doing other work while waiting for a slow operation (like an API call) to finish, instead of blocking everything until it completes.

**Simple example — synchronous (blocking) vs. async:**

```python
# Synchronous — blocks until each call finishes, one after another
def summarize_all_sync(tickets):
    results = []
    for t in tickets:
        results.append(client.messages.create(..., messages=[{"role": "user", "content": t}]))
    return results

# Asynchronous — multiple calls can be "in flight" at once
import asyncio

async def summarize_all_async(tickets):
    async def summarize_one(t):
        return await async_client.messages.create(..., messages=[{"role": "user", "content": t}])
    return await asyncio.gather(*[summarize_one(t) for t in tickets])
```

**Why this matters for Claude integrations:**
- API calls to Claude take time (network + generation time). If you're processing **many** requests, async lets you run them concurrently instead of one-by-one, dramatically reducing total wait time.
- It's especially relevant for **streaming** (Task 2.3) — streamed responses are naturally handled asynchronously, processing chunks as they arrive.

> **Exam tip:** For a small number of sequential, dependent calls (where each depends on the previous result), synchronous code is fine and simpler. For many **independent** calls, async (or batch — Task 2.3) is the better choice.

## 5. Version Control — Tracking Changes Safely

**Version control** (most commonly **Git**) tracks changes to code over time, letting teams collaborate without overwriting each other's work.

**Core concepts:**

| Term | Meaning |
|---|---|
| **Repository (repo)** | The project's full history of tracked files |
| **Commit** | A saved snapshot of changes, with a message describing what changed |
| **Branch** | An independent line of development (e.g., for a new feature) |
| **Merge / Pull Request (PR)** | Combining a branch's changes back into the main codebase, usually after review |

**Simple example — a typical feature workflow:**

```bash
git checkout -b feature/claude-ticket-summarizer   # create a new branch
# ... make code changes ...
git add .
git commit -m "Add Claude-powered ticket summarization endpoint"
git push origin feature/claude-ticket-summarizer
# Open a Pull Request for review before merging into main
```

**Why it matters for AI-powered features specifically:** prompts, system instructions, and tool schemas are **code too** — they should be version-controlled just like application logic, so changes to Claude's behavior are tracked, reviewable, and revertible.

## 6. SDLC Integration — Fitting Into the Software Development Lifecycle

The **SDLC (Software Development Lifecycle)** is the standard sequence a feature goes through: requirements → design → implementation → testing → deployment → maintenance.

```mermaid
flowchart LR
    A[Requirements\n(Domain 2.1)] --> B[Design/Architecture]
    B --> C[Implementation]
    C --> D[Testing/Evaluation]
    D --> E[Deployment]
    E --> F[Maintenance/Monitoring]
    F -.feedback.-> A
```

**How Claude-powered features fit into this lifecycle:**

| SDLC Stage | What's different/extra when Claude is involved |
|---|---|
| Requirements | Functional + infrastructure requirements (Task 2.1) including model-specific needs |
| Design | Choose workflow vs. agent, deployment model, patterns (Domain 1) |
| Implementation | Build prompts, tool integrations, API calls — treated as first-class code |
| Testing | Evaluate model output quality, not just pass/fail unit tests (covered in later domains) |
| Deployment | Consider rollout strategy — model behavior can shift subtly, so gradual rollout matters |
| Maintenance | Monitor for prompt drift, model updates, cost/latency regressions over time |

> **Exam tip:** The key exam idea is that Claude-powered components **don't bypass** the SDLC — they go through the same stages, just with some AI-specific additions (like output quality evaluation) layered in.

## 7. Code Review — Catching Issues Before They Ship

**Code review** is the practice of having another engineer examine changes before they're merged, to catch bugs, security issues, and design problems.

**What to look for in a review that touches Claude integrations:**

| Review Focus | Example Question |
|---|---|
| Correctness | Does the code handle `stop_reason` values correctly (e.g., `tool_use` vs `end_turn`)? |
| Error handling | What happens if the API call fails, times out, or returns malformed output? |
| Security | Is sensitive data (customer PII) being sent to Claude unnecessarily? |
| Cost awareness | Is caching used where appropriate? Is `max_tokens` reasonable? |
| Prompt changes | Are system prompt / tool schema changes reviewed with the same care as code changes? |

> ⚠️ **Anti-Pattern: Reviewing code but not reviewing prompts**
> Treating a system prompt or tool description change as "just text" and skipping proper review. Prompt changes can silently change application behavior just as much as code changes — they deserve the same review rigor.

## 8. Refactoring — Small-Scale and Large-Scale

**Refactoring** means restructuring existing code to improve its design, without changing its external behavior.

### 8.1 Small-Scale Refactoring

Local, contained changes — renaming variables, extracting a function, simplifying a conditional.

**Simple example:**

```python
# Before
def handle(t):
    r = client.messages.create(model="claude-sonnet-4-6", max_tokens=300,
        messages=[{"role": "user", "content": f"Summarize: {t}"}])
    return r.content[0].text

# After — small-scale refactor for clarity
def summarize_ticket(ticket_text: str) -> str:
    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=300,
        messages=[{"role": "user", "content": f"Summarize: {ticket_text}"}]
    )
    return response.content[0].text
```

### 8.2 Large-Scale Refactoring

Structural changes affecting multiple files/modules or the overall architecture — for example, converting a single monolithic agent into a manager/subagent hierarchy (Task 1.1), or migrating from a custom agent loop to the Claude Agent SDK (Task 1.2).

**Why large-scale refactoring needs extra care:**
- Higher risk of breaking existing behavior across many integration points
- Should be done incrementally where possible, with tests/evaluations at each step
- Benefits strongly from version control (small, reviewable commits) rather than one giant change

| Aspect | Small-Scale Refactoring | Large-Scale Refactoring |
|---|---|---|
| Scope | Single function/file | Multiple modules or overall architecture |
| Risk | Low | Higher — more integration points affected |
| Approach | Direct, quick | Incremental, with intermediate testing/evaluation |
| Example | Renaming a variable, extracting a helper function | Splitting a monolithic agent into manager + subagents |

> **Exam tip:** The tested principle is: **larger refactors need smaller, safer steps** — not "just rewrite it all at once." This is especially true for AI-powered systems, where behavior changes can be subtle and hard to catch without evaluation at each step.

## 10. Practice Q&A

**Q1. A developer parses Claude's text output directly as JSON without any error handling. What's the risk, and what's the fix?**
<details><summary>Answer</summary>
The risk is a runtime crash if the model returns malformed or non-JSON text. The fix is to parse defensively (try/except) or use a structured-output approach that enforces a schema.
</details>

**Q2. A team needs to summarize 10,000 independent support tickets as fast as possible using realtime calls. Which programming approach helps most, and why?**
<details><summary>Answer</summary>
**Asynchronous programming** (or the Batch API for very large volumes) — since the tickets are independent, running calls concurrently instead of one at a time dramatically reduces total wait time.
</details>

**Q3. Why should system prompts and tool schemas be stored in version control, just like application code?**
<details><summary>Answer</summary>
Because changes to them can change the application's behavior just as much as code changes — version control makes those changes tracked, reviewable, and revertible.
</details>

**Q4. A team wants to convert a single large agent into a manager/subagent architecture across their whole codebase in one big change. What's the recommended approach instead?**
<details><summary>Answer</summary>
Treat it as a **large-scale refactor** done incrementally, with testing/evaluation at each step — rather than one giant, high-risk rewrite.
</details>

**Q5. True or False: Claude-powered features should bypass the normal SDLC since AI behavior is different from regular code.**
<details><summary>Answer</summary>
False. Claude-powered features go through the same SDLC stages as any software, with some AI-specific additions layered in (like output-quality evaluation during testing) — they don't bypass the lifecycle.
</details>
